# Trip Service — лабораторная работа 1

HTTP API для создания, получения и завершения поездок. Данные и история статусов
хранятся в PostgreSQL. Контракты курса находятся в `contracts/`, сгенерированный
серверный интерфейс — в `internal/generated/`.

## Запуск локально

Нужны Go 1.27.0, Make, работающий Docker и
[`tripgoctl`](https://github.com/course-go-autumn-2026/course-infra).
Go-инструменты `goose` и `oapi-codegen` закреплены в `go.mod`.

В корне репозитория:

```sh
tripgoctl cluster start
tripgoctl environment start
make migrate
make run
```

`tripgoctl environment start` создаёт `.env` с адресом PostgreSQL для этой лабы.
`make run` загружает через shell сначала `.env.example`, затем `.env`:
значения из `.env` переопределяют настройки по умолчанию. Команды миграций
загружают только `.env`.

Для остановки нажмите Ctrl+C: активные запросы завершаются в пределах `SHUTDOWN_TIMEOUT`,
затем закрывается пул.

## Команды

| Команда | Действие |
|---|---|
| `make build` | Собрать `bin/trip-service` |
| `make run` | Собрать и запустить сервис с конфигурацией из env-файлов |
| `make migrate` | Применить все миграции |
| `make migrate-down` | Откатить одну последнюю миграцию |
| `make migrate-status` | Показать состояние миграций |
| `make generate` | Перегенерировать HTTP API и моки зависимостей хендлеров |
| `make test` | Запустить `go test -race ./...` |
| `make lint` | Запустить `golangci-lint run ./...` |
| `make docker-build` | Собрать образ `trip-service:lab1` |
| `make docker-run` | Запустить образ в foreground с доступом к БД `tripgoctl` |
| `make docker-stop` | Остановить контейнер `trip-service` |

`make test` запускает тесты HTTP-хендлеров с `httptest` и `gomock`, проверки
маппинга ошибок, валидации запросов и маршрутизации. Моки генерируются рядом
с хендлерами в `mocks_test.go` через `go:generate` в `contract.go`.
Для `make lint` нужен установленный `golangci-lint` версии 2.
Настройки проверок находятся в `.golangci.yaml`.

## HTTP-слой

Каждая ручка поездок находится в своём пакете:
`internal/http/trip/create`, `get` и `finish`. Хендлер получает юзкейс через
узкий неэкспортируемый интерфейс из своего `contract.go`. Проверки и перевод
тела запроса создания в доменную модель находятся в `create/convert.go`.

Перевод доменной поездки в API-модель общий для всех трёх ручек и находится
в `internal/http/trip/convert.go`: формат ответа одинаков и не зависит
от сценария, поэтому этот код не дублируется по пакетам действий.

`internal/http/domainerror.Problem` сопоставляет ошибки домена с HTTP-статусом
и `api.Problem` через `errors.Is` / `errors.As`. Запись ошибок с заголовком
`application/problem+json` и полем `instance` также собрана в `domainerror`;
неизвестные ошибки возвращаются как `500 internal_error` без внутренних деталей.
Обычные JSON-ответы записывает `internal/http/response`.

`health` и `ready` выделены в отдельные пакеты. Readiness принимает интерфейс
проверки БД и ограничивает вызов `Ping` таймаутом. `internal/http/router.go`
связывает обработчики со сгенерированным серверным интерфейсом и направляет
ошибки разбора параметров маршрута в общий маппер.

## Конфигурация

Все перечисленные переменные обязательны для запуска бинарника. `make run` и
`make docker-run` берут значения по умолчанию из `.env.example`.
Все длительности должны быть больше нуля.

| Переменная | Значение в шаблоне | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | `10s` | Чтение запроса целиком |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Чтение заголовков |
| `HTTP_WRITE_TIMEOUT` | `10s` | Дедлайн записи ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Ожидание следующего запроса в соединении |
| `LOG_LEVEL` | `info` | Читается из конфигурации; настройка логгера пока не реализована |
| `SHUTDOWN_TIMEOUT` | `10s` | Общий бюджет остановки |
| `DATABASE_URL` | Из `.env`, созданного `tripgoctl` | Подключение к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | Максимальное число соединений |
| `DATABASE_MIN_CONNS` | `2` | Минимальное число соединений |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | Максимальный возраст соединения |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | Подключение к БД и стартовый Ping |
| `DATABASE_QUERY_TIMEOUT` | `3s` | Чтение поездки, проверка ready и бюджет транзакции |

## Docker — задание со звёздочкой

`deploy/Dockerfile` использует два этапа: Go 1.27.0 собирает сервис командой
`go build -o /out/trip-service ./cmd/trip-service`, затем бинарник и корневые
TLS-сертификаты копируются в `scratch`.
Процесс работает с UID/GID `65532:65532`. Исходников, Go, shell и кеша сборки
в финальном образе нет. `.dockerignore` исключает Git, локальные конфиги,
инфраструктурные файлы и тесты из контекста сборки.

Сначала поднимите PostgreSQL через `tripgoctl` и выполните `make migrate`,
как в инструкции выше. Остановите локальный экземпляр сервиса, если он занимает
тот же HTTP-порт, затем:

```sh
make docker-build
make docker-run
```

В другом терминале:

```sh
curl -i http://localhost:8080/ready
docker image inspect trip-service:lab1 --format '{{.Size}}'
make docker-stop
```

Контейнер использует `--network host`, чтобы адрес PostgreSQL из `.env` был
доступен без подмены хоста и порта.

В Makefile заданы имя образа `trip-service:lab1`, имя контейнера `trip-service`
и ожидание остановки 15 секунд. `make docker-run` передаёт настройки через
`--env-file .env.example --env-file .env`: значения из `.env` переопределяют
настройки по умолчанию.

Размер локально собранного образа `trip-service:lab1` для `linux/arm64`:
**8 177 712 байт (8,18 MB)** по полю `Size` команды `docker image inspect`.
После изменения сборки или архитектуры измерьте размер заново.

Для проверки запуска `/ready` и `/health` должны возвращать `200` и JSON
`{"status":"ok"}`. Команда `make docker-stop` должна штатно завершать сервис.

## Решения лабораторной работы 1: транзакции

Создание и завершение поездки выполняются через `TxManager.Do`: запись поездки
и добавление строки в `trip_status_history` входят в одну транзакцию. Историю
записывает метод `AddStatusHistory` существующего репозитория поездок:
при создании `NULL → active`, при завершении `active → completed`.
Ошибка записи истории откатывает изменение поездки.

Менеджер хранит `pgx.Tx` в контексте под приватным ключом. Все методы репозитория
выбирают исполнителя через `postgres.Executor`: транзакцию из контекста либо
пул. Вложенный `Do` использует ту же транзакцию; callback должен возвращать
ошибки вложенных операций наружу. Коммит выполняет только внешний `Do`.
При ошибке или панике вызывается rollback, паника распространяется дальше.

Уровень изоляции — `READ COMMITTED`
От повторного завершения защищает `UPDATE ... WHERE status = 'active'`.
Если обновление не затронуло строк, сервис повторно читает поездку:
при этой изоляции новый запрос видит изменения,
зафиксированные параллельной транзакцией, и различает отсутствие поездки
и её завершение. История добавляется только после успешного обновления.
От двух активных поездок одного водителя
защищает частичный уникальный индекс.

Менеджер получает `DATABASE_QUERY_TIMEOUT` из `main` и ограничивает им внешний
`Do`, включая начало транзакции и коммит. Для rollback создаётся отдельный
контекст с тем же таймаутом, независимый от отмены исходного запроса.

Обычное чтение поездки ограничено `DATABASE_QUERY_TIMEOUT` в репозитории;
более ранний дедлайн родительского контекста сохраняется.
